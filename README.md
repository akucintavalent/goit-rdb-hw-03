# Домашня робота №3 — Seoul Bike Sharing Demand

**Курс:** Реляційні бази даних  
**Тема:** Завантаження даних та основи SQL (DQL-команди)  
**Варіант:** D — UCI Seoul Bike Sharing Demand  
**Основний файл:** [`goit_rdb_hw_03.ipynb`](goit_rdb_hw_03.ipynb)

## Дані та джерело

Використано **повний** набір `SeoulBikeData.csv` із [UCI Machine Learning Repository, Seoul Bike Sharing Demand (ID 560)](https://archive.ics.uci.edu/dataset/560/seoul+bike+sharing+demand). Пряме посилання на офіційний [ZIP-архів](https://archive.ics.uci.edu/static/public/560/seoul+bike+sharing+demand.zip) вбудоване в notebook. Пошук і ручне завантаження файлу не потрібні.

- **Обсяг:** 8 760 рядків (365 днів × 24 години), 14 початкових колонок; вибірка не скорочувалася.
- **Період:** 01.12.2017–30.11.2018.
- **Гранулярність:** одне погодинне спостереження про кількість оренд у Сеулі з погодними та календарними характеристиками.
- **CSV:** роздільник `,`, заголовок у першому рядку, кодування `ISO-8859-1`.
- **Локальний шлях:** `data/SeoulBikeData.csv`. Notebook створює `data/` і завантажує/розпаковує файл, якщо CSV ще не існує.

## Відтворення роботи у Google Colab

1. Відкрийте `goit_rdb_hw_03.ipynb` у [Google Colab](https://colab.research.google.com/).
2. Відкрийте `Середовище виконання` → `Змінити тип середовища виконання` → `Версія середовища виконання` і оберіть `2026.04`.
3. Оберіть **Runtime → Restart session and run all** (або послідовно виконайте всі клітинки зверху вниз). Потрібні інтернет-доступ для встановлення залежностей і завантаження архіву та стандартне середовище Colab.
4. Перша кодова клітинка встановлює `pgserver`, `psycopg2-binary`, `sqlalchemy`, `pandas`, `pyarrow`, `ucimlrepo`, `sqlparse`, запускає локальний PostgreSQL і показує `SELECT version()`.
5. Notebook автоматично завантажує вихідний CSV з UCI, створює staging-таблицю та імпортує дані через PostgreSQL `COPY FROM STDIN` (`psycopg2.copy_expert`).
6. Наступні клітинки створюють типізовану таблицю через DDL, переносять дані через `INSERT INTO ... SELECT`, виконують SQL-аудит і аналітичні запити. Вивід збережено в notebook.

**Примітка:** `pgserver` працює у тимчасовому середовищі Colab: після скидання сесії базу потрібно створити знову, виконавши notebook від початку. Скрипт скидає власні таблиці `hw3_data_staging` і `hw3_data_clean` перед повторним імпортом. Якщо `data/SeoulBikeData.csv` уже є, він повторно не завантажується.

## Структура notebook

| Розділ | Зміст |
|---|---|
| 1. Setup і завантаження | Налаштування PostgreSQL, допоміжна `execute_sql()`, отримання даних з UCI. |
| 2. Staging і DDL | Staging з усіма сирими полями типу `TEXT`; `COPY FROM STDIN`; профілювання, обґрунтування типів, `PRIMARY KEY`, `NOT NULL`, предметні `CHECK`; перенесення `INSERT INTO ... SELECT`. |
| 3. Data-quality audit | Порівняння кількості рядків, дублікати за `(Date, Hour)` і повними рядками, NULL-rate, порожні рядки й спеціальні маркери. |
| 4. Розподіли та аномалії | Категоріальні розподіли, числова статистика оренд, правило 3σ для температури, доменна перевірка нульової вологості. |
| 5. Десять DQL/EDA-запитів | Для кожного: business-question, SQL та інтерпретація; разом покривають обов'язкові конструкції Теми 3. |
| 6. Reflection | Якість даних, ML-ознаки, ризик data leakage, пропозиції до pipeline та прогнозування попиту. |

## Основні результати виконання

- У staging та clean — **по 8 760 рядків**; після перенесення втрат немає.
- За природним ключем `(Date, Hour)` і за повними змістовними рядками дублікатів не виявлено.
- Перевірки staging не знайшли SQL `NULL`, порожніх рядків і спеціальних маркерів; перевірені колонки clean мають 0% `NULL`.
- Доменна перевірка виявила **17 годин із нульовою вологістю**: ці значення запропоновано перевірити за джерелом, а не безпідставно видаляти рядки.
- **295 годин простою** прокату мають нульову кількість оренд; це важливо враховувати під час побудови моделі попиту.

Ці числа відповідають збереженим результатам SQL-клітинок у notebook. Повний код аналізу й детальні інтерпретації наведені там само.
